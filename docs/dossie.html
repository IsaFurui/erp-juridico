Como rodar

O que mudou desde o levantamento anterior (pós-Fase 3). A Fase 4 entregou o dashboard: a primeira tela deixou de ser o "em construção" e virou a visão do escritório — cards de KPI (processos em aberto, encerrados e ganho no mês, clientes ativos, valor em curso), um donut de processos por status, atividade recente (as últimas mudanças de status, de quem e quando) e, para quem pode, a despesa do mês. Tudo vem agregado do backend num GET /dashboard só, sem nenhuma migration (os dados já existiam). O bloco financeiro é gated: OPERACIONAL recebe finance: null e a tela esconde esses números. Este documento descreve o estado da branch feat/fase-4-dashboard.

Do zero, numa máquina onde o projeto não roda faz tempo. Termina com dois terminais abertos: um do backend, um do frontend.

  1. Subir o Postgres

    # na raiz do projeto
docker compose up -d postgres

    Só o serviço postgres. O serviço backend do compose ainda não recebe as variáveis de JWT e quebra no boot — isso é da Fase 5.

  2. Criar o .env do backend

    cd backend
cp .env.example .env

    Preencher JWT_SECRET e, principalmente, PLATFORM_ADMIN_PASSWORD — sem ela o seed não cria o usuário root, e sem root não há como entrar. DATABASE_URL já vem apontando para o Postgres do compose.

  3. Instalar dependências e gerar o client do Prisma

    npm install
npx prisma generate      # cria generated/prisma, que não vai para o git

  4. Aplicar as migrations

    npx prisma migrate deploy

    São seis, a última é 20261024033015_add_expense_category_and_date. migrate dev só quando estiver alterando o schema. Puxou a branch e o seed reclama de isFinal? Rode prisma generate e migrate deploy antes — ver a tabela no fim desta seção.

  5. Rodar o seed

    npx prisma db seed

    Popula os catálogos (13 status, 10 tipos) e cria o administrador da plataforma com o login e a senha do .env. É idempotente — e rodar de novo com outra PLATFORM_ADMIN_PASSWORD redefine a senha do root. Esse é o caminho de recuperação, já que a API não cria nem promove ninguém a esse papel.

  6. Subir o backend

    npm run start:dev        # http://localhost:3000

    Swagger em /api/docs; o botão Authorize aceita o JWT.

  7. Subir o frontend

    # outro terminal, a partir da raiz
cd frontend
npm install
npm run dev              # http://localhost:5173

    O Vite faz proxy de /api para a porta 3000 — é por isso que ainda funciona sem CORS no backend.

  8. Primeiro acesso: entrar como plataforma

    Na tela de login, aba Plataforma — ela não pede ID de empresa. Use PLATFORM_ADMIN_LOGIN e PLATFORM_ADMIN_PASSWORD.

  9. Cadastrar um escritório e o ADMIN dele

    Em Plataforma → Empresas, criar a empresa. Na linha dela, o botão Usuários abre o cadastro de usuários daquele escritório — é ali que nasce o primeiro ADMIN. O ID da empresa está na primeira coluna da lista: ele é pedido no login do escritório.

  10. Entrar como o escritório

    Sair, voltar ao login na aba Escritório, usar o ID da empresa mais o login do ADMIN recém-criado. A sessão da plataforma não enxerga dado de escritório (recebe 403 em /clients e /processes), então o produto se testa por aqui.

01

Modelo de dados

Dez tabelas, seis migrations. O multi-tenant é feito por coluna: companyId em User, Client, Expense e Process. Duas coisas ficam de fora dessa árvore de propósito: os catálogos de status e tipo, que são globais e compartilhados por todos os escritórios, e o PlatformAdmin, que é o dono da plataforma e não pertence a empresa nenhuma. A décima tabela é a mais nova: ProcessStatusHistory, o livro de registro que ganha uma linha a cada mudança de status e nunca sobrescreve.

Regras já gravadas no schema

RegraOndeEfeito
@@unique([companyId, login]) User O mesmo login pode existir em empresas diferentes — por isso o login de escritório pede o ID da empresa.
login @unique PlatformAdmin Único global: o root não tem empresa, então não há par (empresa, login) para desempatar.
@@unique([companyId, cpfCnpj]) Client Um CPF/CNPJ pode ser cliente de mais de um escritório.
code @unique Process Número do processo é único global, não por empresa — divergente do padrão das outras tabelas. Dois escritórios não conseguem cadastrar o mesmo número.
subtypeId Int? Process Subtipo entrou como FK opcional (migration add_process_subtype_fk). O combo dependente tipo → subtipo já está no formulário da tela de processos.
isFinal ProcessStatus Flag nova (migration process_status_history_and_final_flag). Marca os 5 status que encerram o processo — e é só neles que o totalAmount destrava para edição manual.
totalAmount @default(0) Process Derivado de fixedAmount + expectedAmount enquanto o processo corre; preservado como valor manual depois que ele é encerrado. Não é mais um número solto.
onDelete: Restrict todas as FKs Nada é apagado em cascata. Inativação é por flag active em Company, Client e PlatformAdmin; Process e Expense não têm essa flag.
Decimal(12, 2) valores Dinheiro em decimal, não float — correto. Chega no JSON como string; quem consumir precisa converter.
UserRole enum ADMIN FINANCEIRO OPERACIONAL — papéis dentro de um escritório. FINANCEIRO ainda não gate nenhuma rota.
active Company Desde a Fase 0 o login recusa usuário de empresa inativa — antes a flag não tinha efeito nenhum.

04

Furos e bugs encontrados

Os quatro furos críticos do levantamento original estão fechados. O companyId hoje vem sempre do token; company é exclusivo da plataforma; GET /clients e GET /users filtram por empresa; e PATCH /users/:id responde 404 para usuário de outro escritório. Há um e2e de isolamento com 26 casos — e a Fase 2 somou um e2e de processos — além dos 54 testes unitários. Nada do que sobrou abaixo é vazamento entre escritórios.

  1. Usuários ainda sem paginação médio

    Clientes (Fase 1) e processos (Fase 2) já reusam a base em common/ — PaginationQueryDto e o envelope Paginated. Sobrou GET /users, que ainda devolve a lista inteira, sem skip/take, ordenação ou busca. É o que falta para fechar o padrão em todas as listas.

    users.service.ts:67

  2. Sem CORS — só funciona atrás do proxy do Vite alto

    main.ts não chama app.enableCors(). Em dev o proxy do Vite esconde isso porque tudo sai da mesma origem. No dia em que o front subir num domínio separado, todas as requests morrem no preflight.

    backend/src/main.ts:7

  3. O compose não sobe alto

    O serviço backend só recebe DATABASE_URL. JwtModule e JwtStrategy usam getOrThrow em JWT_SECRET e JWT_EXPIRES_IN, então o container quebra no boot. O frontend não está no compose.

    docker-compose.yml:26

  4. Deletar catálogo em uso devolve 500 médio

    DELETE em status e tipo faz delete físico. Com um processo apontando para o registro, o onDelete: Restrict estoura um PrismaClientKnownRequestError que ninguém captura — vira 500 em vez de 409. Agora que processos existem de verdade, é fácil de encostar nisso.

    process-status.service.ts:53 · process-type.service.ts:58

  5. Processo é apagado de verdade médio

    DELETE /processes/:id remove a linha. Process não tem flag active, então não existe o padrão de inativação que Company e Client usam — e um processo apagado por engano não volta.

    backend/src/process/process.service.ts:120

  6. Número de processo é único no SaaS inteiro médio

    code @unique não inclui companyId, e ensureCodeAvailable busca sem filtro de empresa. Dois escritórios que atuem no mesmo processo — coisa comum — não conseguem cadastrá-lo: o segundo recebe 409. Divergente de User e Client, que são únicos por empresa.

    backend/prisma/schema.prisma:110 · process.service.ts:123

  7. Auditoria só existe para o status do processo médio

    A Fase 2 trouxe ProcessStatusHistory, que registra quem mudou o status, quando e com que observação — a primeira trilha de auditoria do sistema. Fora disso, nada registra quem criou ou alterou o quê: não há createdBy nas demais tabelas nem log de eventos. Num sistema onde a plataforma pode agir dentro de qualquer escritório, é o registro que explicaria uma alteração inesperada depois.

    restante do backend

  8. O root não tem como recuperar a senha pela aplicação médio

    PATCH /auth/platform/me/password exige a senha atual, e a API não cria nem promove ninguém a PlatformAdmin — por desenho. Perdida a senha, o conserto é rodar o seed de novo com uma nova PLATFORM_ADMIN_PASSWORD, ou seja, é preciso acesso ao servidor.

    backend/prisma/seed.ts
05

Rota para terminar

As fases estão em ordem de dependência, não de preferência. As Fases 0 a 4 saíram — a fronteira do tenant, clientes, o núcleo de processos, o financeiro e o dashboard. Resta a Fase 5, o endurecimento para produção. As estimativas assumem você trabalhando sozinha nesse ritmo.

Fase 0

Fechar a fronteira do tenant

concluída
  • Guards no company: módulo inteiro exclusivo da plataforma, POST incluído.
  • clients e users escopados: companyId sempre do token; GET /users/company/:companyId virou GET /users.
  • register sem companyId confiável no body: ADMIN cria só na própria empresa.
  • Root fora da tabela User: PlatformAdmin, dois escopos de token, três guards (RolesGuard, PlatformGuard, RequireTenantGuard).
  • exp checado no front dentro de readStoredToken.
  • Empresa inativa não loga mais — a flag passou a ter efeito.
  • Testes: 29 unitários + e2e de isolamento com 22 casos (hoje são 37 e 26, com o que a Fase 1 acrescentou).
Fase 1

Terminar clientes

concluída
  • Base de paginação em common/: PaginationQueryDto (page, pageSize com teto 100, search) e o envelope { items, total, page, pageSize, pages } — escrito para processos reusar.
  • Listagem de clientes paginada e ordenada por nome, com busca por nome ou documento. O termo é normalizado para dígitos antes de casar com o CPF/CNPJ, que é gravado sem pontuação.
  • Na tela: busca com debounce, contador, paginação, e recarga da lista depois de cada escrita — remendar o array local erraria o total.
  • GET /process-status liberado para JWT: o guard saiu da classe e foi para as rotas de escrita. Era o bloqueio da tela de processos.
  • ?includeInactive restrito a ADMIN no service — e não com RolesGuard, porque a rota precisa continuar aberta a todos os papéis; só a flag é de ADMIN.
  • Lint da ClientsPage resolvido: o efeito não chama mais setState no corpo, só nos callbacks.
Fase 2

Processos — a tela do núcleo

concluída

  • ProcessesPage em cartões: busca por nome ou número, filtros por status, tipo e cliente, badge de status e paginação — reusando a base de common/.

06

Decisões em aberto

Escolhas de produto que o código ainda não tomou. Três já saíram: subtipo entrou no schema (FK opcional em Process); a regra de valores foi decidida na Fase 2; e o vínculo da despesa foi resolvido na Fase 3 — é custo do escritório, sem FK a processo ou cliente, organizada por categoria. As de baixo continuam.

  1. Receita: o escritório acompanha o que entra? abre a próxima fase do financeiro

    O schema só modela despesa. Honorários recebidos — o dinheiro que entra — não têm tabela. A Fase 3 foi deliberadamente só de saída; se o escritório precisa de fluxo de caixa (entradas × saídas, resultado do mês), falta uma tabela de receita e, aí sim, talvez o vínculo com o processo que gerou o honorário.

  2. Catálogo global ou por escritório? segue em aberto

    A Fase 2 embarcou com o catálogo global: ProcessStatus e ProcessType não têm companyId, e o description / name é único global. Consequência: um ADMIN que renomeia um status muda para todos os escritórios, e ninguém pode ter um status próprio. Manter global e tirar a escrita dos ADMINs de escritório, ou adicionar companyId opcional (nulo = padrão do sistema) — as duas são defensáveis, mas são caminhos diferentes, e a tela de processos já consome esse catálogo como ele está.

  3. Quem pode ver o processo de quem? regra de negócio

    O isolamento é por empresa e o RBAC é por papel. Não existe noção de advogado responsável: Process não tem userId. Se um escritório precisa que cada advogado veja só a própria carteira, isso é coluna nova mais filtro — e sai mais barato decidir antes da tela de processos que depois.

  4. O login do escritório vai continuar pedindo o ID da empresa? UX

    Metade disso foi resolvida: a plataforma entra por uma aba própria e não pede empresa. Para o escritório o atrito continua — a tela pede um número, e o número só aparece na lista de empresas do root. Alternativas: slug ou subdomínio do escritório, ou tornar o login único global (e-mail) e descobrir a empresa pelo usuário. A segunda mexe no @@unique([companyId, login]), então é migration.

  5. Número de processo único por empresa ou global? regra de negócio

    Hoje é global (seção 04), o que impede dois escritórios de cadastrarem o mesmo processo. Se clientes diferentes podem contratar escritórios diferentes no mesmo caso — e podem — isso vira @@unique([companyId, code]) e uma migration.
