Como rodar

O que mudou desde o primeiro levantamento (22 out). A Fase 0 foi implementada: o módulo company ficou fechado, clients e users passaram a ser escopados por empresa, e o dono da plataforma saiu da tabela User para uma tabela própria, PlatformAdmin, fora da árvore de Company — por isso a tela de login agora tem dois modos. Depois disso, um merge com a main trouxe o módulo de processos e a tela de clientes. Depois disso, a Fase 2 entregou a tela de processos inteira — lista em cartões, página própria e histórico de status —, com a regra dos três valores e a tabela de histórico no backend. Este documento descreve o estado da main pós-Fase 2 (merge do PR #2).

Do zero, numa máquina onde o projeto não roda faz tempo. Termina com dois terminais abertos: um do backend, um do frontend.

  1. Subir o Postgres

    # na raiz do projeto
docker compose up -d postgres

    Só o serviço postgres. O serviço backend do compose ainda não recebe as variáveis de JWT e quebra no boot — isso é da Fase 5.

  2. Criar o .env do backend

    cd backend
cp .env.example .env

    Preencher JWT_SECRET e, principalmente, PLATFORM_ADMIN_PASSWORD — sem ela o seed não cria o usuário root, e sem root não há como entrar. DATABASE_URL já vem apontando para o Postgres do compose.

  3. Instalar dependências e gerar o client do Prisma

    npm install
npx prisma generate      # cria generated/prisma, que não vai para o git

  4. Aplicar as migrations

    npx prisma migrate deploy

    São quatro, a última é 20261022120000_platform_admin. migrate dev só quando estiver alterando o schema.

  5. Rodar o seed

    npx prisma db seed

    Popula os catálogos (13 status, 10 tipos) e cria o administrador da plataforma com o login e a senha do .env. É idempotente — e rodar de novo com outra PLATFORM_ADMIN_PASSWORD redefine a senha do root. Esse é o caminho de recuperação, já que a API não cria nem promove ninguém a esse papel.

  6. Subir o backend

    npm run start:dev        # http://localhost:3000

    Swagger em /api/docs; o botão Authorize aceita o JWT.

  7. Subir o frontend

    # outro terminal, a partir da raiz
cd frontend
npm install
npm run dev              # http://localhost:5173

    O Vite faz proxy de /api para a porta 3000 — é por isso que ainda funciona sem CORS no backend.

  8. Primeiro acesso: entrar como plataforma

    Na tela de login, aba Plataforma — ela não pede ID de empresa. Use PLATFORM_ADMIN_LOGIN e PLATFORM_ADMIN_PASSWORD.

  9. Cadastrar um escritório e o ADMIN dele

    Em Plataforma → Empresas, criar a empresa. Na linha dela, o botão Usuários abre o cadastro de usuários daquele escritório — é ali que nasce o primeiro ADMIN. O ID da empresa está na primeira coluna da lista: ele é pedido no login do escritório.

  10. Entrar como o escritório

    Sair, voltar ao login na aba Escritório, usar o ID da empresa mais o login do ADMIN recém-criado. A sessão da plataforma não enxerga dado de escritório (recebe 403 em /clients e /processes), então o produto se testa por aqui.

01

Modelo de dados

Dez tabelas, cinco migrations (a última adiciona o histórico de status). O multi-tenant é feito por coluna: companyId em User, Client, Expense e Process. Duas coisas ficam de fora dessa árvore de propósito: os catálogos de status e tipo, que são globais e compartilhados por todos os escritórios, e o PlatformAdmin, que é o dono da plataforma e não pertence a empresa nenhuma.

Regras já gravadas no schema

RegraOndeEfeito
@@unique([companyId, login]) User O mesmo login pode existir em empresas diferentes — por isso o login de escritório pede o ID da empresa.
login @unique PlatformAdmin Único global: o root não tem empresa, então não há par (empresa, login) para desempatar.
@@unique([companyId, cpfCnpj]) Client Um CPF/CNPJ pode ser cliente de mais de um escritório.
code @unique Process Número do processo é único global, não por empresa — divergente do padrão das outras tabelas. Dois escritórios não conseguem cadastrar o mesmo número.
subtypeId Int? Process Subtipo entrou como FK opcional (migration add_process_subtype_fk). O combo tipo → subtipo já tem endpoint de leitura.
onDelete: Restrict todas as FKs Nada é apagado em cascata. Inativação é por flag active em Company, Client e PlatformAdmin; Process e Expense não têm essa flag.
Decimal(12, 2) valores Dinheiro em decimal, não float — correto. Chega no JSON como string; quem consumir precisa converter.
UserRole enum ADMIN FINANCEIRO OPERACIONAL — papéis dentro de um escritório. FINANCEIRO ainda não gate nenhuma rota.
active Company Desde a Fase 0 o login recusa usuário de empresa inativa — antes a flag não tinha efeito nenhum.
isFinal ProcessStatus Flag da Fase 2 que marca os 5 status de encerramento (Encerrado com êxito/sem êxito, Acordo celebrado, Arquivado, Prescrito). É ela que destrava a edição do totalAmount — em vez de chumbar nomes no código.
totalAmount Process Agora tem regra: enquanto o status não é isFinal, o service grava fixedAmount + expectedAmount (travado). Num status de encerramento, o advogado pode informar o Total real; reabrir volta a derivar.

04

Furos e bugs encontrados

Os quatro furos críticos do levantamento original estão fechados. O companyId hoje vem sempre do token; company é exclusivo da plataforma; GET /clients e GET /users filtram por empresa; e PATCH /users/:id responde 404 para usuário de outro escritório. Há um e2e de 26 casos e 37 testes unitários cobrindo exatamente essa classe de bug. Nada do que sobrou abaixo é vazamento entre escritórios.

  1. Usuários ainda sem paginação médio

    Processos foi resolvido na Fase 2 (reusou a base de common/). Agora só o GET /users continua devolvendo a lista inteira, sem skip/take, ordenação ou busca. A base (PaginationQueryDto + envelope Paginated) já está pronta para ele.

    users.service.ts:67

  2. Sem CORS — só funciona atrás do proxy do Vite alto

    main.ts não chama app.enableCors(). Em dev o proxy do Vite esconde isso porque tudo sai da mesma origem. No dia em que o front subir num domínio separado, todas as requests morrem no preflight.

    backend/src/main.ts:7

  3. O compose não sobe alto

    O serviço backend só recebe DATABASE_URL. JwtModule e JwtStrategy usam getOrThrow em JWT_SECRET e JWT_EXPIRES_IN, então o container quebra no boot. O frontend não está no compose.

    docker-compose.yml:26

  4. Deletar catálogo em uso devolve 500 médio

    DELETE em status e tipo faz delete físico. Com um processo apontando para o registro, o onDelete: Restrict estoura um PrismaClientKnownRequestError que ninguém captura — vira 500 em vez de 409. Agora que processos existem de verdade, é fácil de encostar nisso.

    process-status.service.ts:53 · process-type.service.ts:58

  5. Delete físico de processo ainda existe no backend mitigado

    DELETE /processes/:id continua removendo a linha, e Process não tem flag active. A Fase 2 tirou o botão de apagar da tela — "encerrar" virou o status Arquivado —, então o risco pela interface sumiu. Mas a rota segue aberta a um ADMIN que a chame direto.

    backend/src/process/process.service.ts

  6. totalAmount agora tem regra resolvido

    Resolvido na Fase 2. O service deriva totalAmount = fixedAmount + expectedAmount enquanto o processo não está encerrado, e só aceita o valor manual quando o status é de encerramento (isFinal). Reabrir volta a derivar. A edição de dados recalcula; a mudança de status reconcilia.

    backend/src/process/process.service.ts

  7. Número de processo é único no SaaS inteiro médio

    code @unique não inclui companyId, e ensureCodeAvailable busca sem filtro de empresa. Dois escritórios que atuem no mesmo processo — coisa comum — não conseguem cadastrá-lo: o segundo recebe 409. Divergente de User e Client, que são únicos por empresa.

    backend/prisma/schema.prisma:110 · process.service.ts:123

  8. Não existe auditoria médio

    Nada registra quem criou ou alterou o quê: nem createdBy nas tabelas, nem log de eventos. Num sistema onde a plataforma pode agir dentro de qualquer escritório, é o registro que explicaria uma alteração inesperada depois.

    todo o backend

  9. backend/CLAUDE.md está meio atualizado médio

    As seções de autenticação, escopos e RBAC foram reescritas na Fase 0. O resto do arquivo — a parte de users/ e a de Prisma — ainda documenta o schema antigo em português (Usuario, UsuSenhaHash, findAllByEmpresa), que deixou de existir no commit e5bc02d.

    backend/CLAUDE.md

  10. O root não tem como recuperar a senha pela aplicação médio

    PATCH /auth/platform/me/password exige a senha atual, e a API não cria nem promove ninguém a PlatformAdmin — por desenho. Perdida a senha, o conserto é rodar o seed de novo com uma nova PLATFORM_ADMIN_PASSWORD, ou seja, é preciso acesso ao servidor.

    backend/prisma/seed.ts

06

Decisões em aberto

Escolhas de produto. A Fase 2 fechou duas (a regra dos valores e a visibilidade dos processos). A que bloqueia a próxima fase é a da despesa; as demais seguem abertas, mas sem travar nada por enquanto.

  1. Como somar o valor do processo? decidido · Fase 2

    Resolvido. fixedAmount é a Entrada (o que o cliente paga no começo); expectedAmount é o êxito esperado; totalAmount é a soma dos dois, materializada na escrita e travada enquanto o processo corre. Ao encerrar (status isFinal), o advogado ajusta o Total para o que realmente entrou.

  2. A despesa pertence a quê? decidido

    Resolvido: a despesa é custo do escritório, não do caso. Expense fica como está — só companyId, sem FK para Process nem Client. A Fase 3 não vai adicionar processId; o módulo é de custos gerais do escritório.

  3. Catálogo global ou por escritório? ainda aberta · não bloqueia mais

    ProcessStatus e ProcessType não têm companyId, e o description / name é único global. Consequência: um ADMIN que renomeia um status muda para todos os escritórios, e ninguém pode ter um status próprio. Manter global e tirar a escrita dos ADMINs de escritório, ou adicionar companyId opcional (nulo = padrão do sistema) — as duas são defensáveis, mas são caminhos diferentes. A decisão também resolve o furo de leitura da seção 04.

  4. Quem pode ver o processo de quem? decidido · Fase 2

    Resolvido para já: todos os usuários do escritório veem todos os processos do escritório. Não há advogado responsável — Process segue sem userId. Se um dia um escritório precisar que cada advogado veja só a própria carteira, aí entram a coluna e o filtro; por ora, não.

  5. O login do escritório vai continuar pedindo o ID da empresa? UX

    Metade disso foi resolvida: a plataforma entra por uma aba própria e não pede empresa. Para o escritório o atrito continua — a tela pede um número, e o número só aparece na lista de empresas do root. Alternativas: slug ou subdomínio do escritório, ou tornar o login único global (e-mail) e descobrir a empresa pelo usuário. A segunda mexe no @@unique([companyId, login]), então é migration.

  6. Número de processo único por empresa ou global? regra de negócio

    Hoje é global (seção 04), o que impede dois escritórios de cadastrarem o mesmo processo. Se clientes diferentes podem contratar escritórios diferentes no mesmo caso — e podem — isso vira @@unique([companyId, code]) e uma migration.
